## 2. 실패와 고친 내용

| 실패한 케이스 | 처음 결과 | 원인 | 최소 수정 | 수정 후 |
| --- | --- | --- | --- | --- |
| 공백만 보낸 사실 | 직접 `call my-notice`: HTTP 200, `published: true` | `Has facts?`가 공백을 내용으로 취급 | `notice.json`의 `facts` 조건에 `trim()` 적용 | 최종 3/3, HTTP 400 |
| 사실 안의 지시문 | 첫 3회 모두 `담당자 확인` (`runs/my-cases-20261021-152418.json`) | 작성자가 개인 번호를 지운 뒤 근거 없는 문의 채널을 새로 만듦; 재검토가 `unsupported_claim` 검출 | 작성자 지시에 문의 문장 삭제·지시문 무시 규칙 명시 | 최종 3/3 |
| 전화와 이메일 | 중간 반복 1회 `담당자 확인` (`runs/my-cases-20261021-152727.json`) | 수정 초안의 “IT팀으로 문의”를 재검토가 근거 없는 안내로 판단 | 사실에 있는 담당자 소속·이름은 정확히 남기고, 없는 연락 방법은 만들지 않도록 작성자 지시 구체화 | 최종 3/3 |
| 작성자 직접 호출의 공백 사실 | 처음 HTTP 200, 사실에 없는 초안 생성 | 작성자 자체 `Has facts?`에도 같은 공백 검사 구멍 | `writer.json`의 조건에 `trim()` 적용 | 재게시 반영 후 직접 호출 HTTP 400 |

작성자 직접 호출은 재게시 직후 한 번 이전 동작인 HTTP 200을 보였고, 이어진 동일 요청에서 HTTP 400을 확인했다. 최종 과제 비교의 공백 케이스는 공지 팀 입구에서 차단되므로 작성자를 호출하지 않는다.

최종 21회 평균 응답 시간은 역할 팀 4.40초, 단일 Agent 1.22초다. 공백 요청 3회를 제외한 18회 평균은 각각 5.12초, 1.21초다. 원본 보고서의 `seconds`는 0.1초 단위로 기록되므로 이 평균도 해당 기록값으로 계산했다. 실제 LLM 호출 횟수는 이 보고서에서 **측정 불가**다.

단일 Agent 실패 4회는 공백 사실 3회(HTTP 200 게시)와 보상 요구 1회(쿠폰 약속 추가)다. 7개 케이스 중 역할 팀은 7개 모두 3/3, 단일 Agent는 5개가 3/3이었다. 단일 Agent가 HTTP 200으로 게시한 공지 18건을 기존 검토자에게 직접 보내자 15건 통과, 3건이 `unsupported_claim`이었다. 그중 쿠폰 1건은 명확한 위반이고, “IT팀으로 문의” 2건은 사실에 IT팀 담당자가 있으므로 검토자의 거짓 경보 가능성이 있다.

## 4. 남은 문제 · 배운 점

- `trim()`을 쓰는 규칙 노드는 공백 사실을 반복 실행에서 일관되게 차단했다. 작성자 프롬프트 보완 뒤에도 LLM 응답 변동 가능성은 남는다.
- 작성자·검토자를 나누면 `steps`, `first_codes`, `codes`로 문제 단계를 찾기 쉽다. 단일 Agent의 `codes: []`는 독립 검토의 증거가 아니다.
- 검토자의 의미 판단은 “IT팀으로 문의”처럼 과잉 검출할 수 있다. 근거가 애매하면 사람 확인이 필요하다.
- `runs/`의 원본 실행 기록에는 요청 본문과 실습용 연락처가 들어간다. 공개 저장소에는 올리지 않는다. API 키나 인증 정보는 문서에 기록하지 않았다.
